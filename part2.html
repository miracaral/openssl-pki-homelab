In Part 1 I generated an RSA key pair. In this part I turn keys into a working PKI: a Root CA, two intermediate CAs (one RSA, one ECC), server and user certificates, a signed document verified through the chain, and a revoked certificate caught by a CRL. Everything runs on Kali Linux with OpenSSL 3.x.

What we are building

This is the hierarchy we end up with:

Homelab Root CA (RSA 4096, 20 years)
├── www.homelab.test (server, RSA 2048, 375 days)
├── Homelab Intermediate CA (RSA 4096, 10 years, pathlen:0)
│   ├── Homelab User (RSA 2048, 375 days)
│   └── Revoked Test User (RSA 2048, revoked: keyCompromise)
└── Homelab Intermediate CA 2 ECC (P-384, 10 years, pathlen:0)
    └── Homelab ECC User (P-256, 375 days)

Everything below runs as root, because the CA directories live under /root:

sudo -i

Step 1: The Root CA

A Certificate Authority signs other people's public keys. Everything in the PKI is trusted only because the root is trusted, so the root gets the strongest key and the strictest permissions.

Directory layout

mkdir -p /root/ca && cd /root/ca
mkdir certs crl newcerts private
chmod 700 private
touch index.txt
echo 1000 > serial
echo 1000 > crlnumber
  • index.txt is the CA's database of every certificate it issued.
  • serial holds the next serial number; crlnumber numbers the revocation lists.
  • private/ is 700 because the root private key lives there.

The config file

I started from the widely used sample openssl.cnf from Jamie Nguyen's OpenSSL Certificate Authority guide and changed what did not fit my setup:

sed -i 's/^countryName_default.*/countryName_default = CZ/; s/^stateOrProvinceName_default.*/stateOrProvinceName_default = Prague/; s/^0\.organizationName_default.*/0.organizationName_default = Homelab/; s/^default_bits.*/default_bits = 4096/; /^nsCertType/d; /^nsComment/d' openssl.cnf
  • The sample defaults (GB, England, Alice Ltd) became my real values.
  • default_bits went from 2048 to 4096 to match the key size used for CAs.
  • The nsCertType and nsComment lines are Netscape-era extensions that modern clients ignore, so I removed them.

The root uses policy_strict: it only signs requests whose country, state and organization match its own. Keep that in mind for Step 3.

Root key and self-signed certificate

openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:4096 -aes-256-cbc -out private/ca.key.pem
chmod 400 private/ca.key.pem

openssl req -config openssl.cnf -key private/ca.key.pem -new -x509 -days 7300 -sha256 -extensions v3_ca -out certs/ca.cert.pem
chmod 444 certs/ca.cert.pem

For the Common Name I entered Homelab Root CA. Then inspect it:

openssl x509 -noout -text -in certs/ca.cert.pem

What to check in the output:

  • Issuer and Subject are identical. That is what self-signed means.
  • Public-Key: (4096 bit) and sha256WithRSAEncryption
  • Validity of 20 years
  • X509v3 Basic Constraints: critical, CA:TRUE

Step 2: A CSR and a server certificate

A Certificate Signing Request (CSR) carries a public key and the identity it should be bound to. The CA checks it and returns a signed certificate.

cd /root/ca
openssl req -new -newkey rsa:2048 -nodes -keyout private/server.key.pem -out server.csr -subj "/C=CZ/ST=Prague/O=Homelab/CN=www.homelab.test"
chmod 400 private/server.key.pem
openssl req -in server.csr -noout -text
  • -nodes leaves the server key unencrypted, so a web server can start without someone typing a pass phrase.
  • C, ST and O match the root, because policy_strict requires it.

Sign it with the root:

openssl ca -config openssl.cnf -extensions server_cert -days 375 -notext -md sha256 -in server.csr -out certs/server.cert.pem

OpenSSL prints Signature ok, shows the details (CA:FALSE, Digital Signature, Key Encipherment, TLS Web Server Authentication), and asks twice for confirmation. Then verify:

openssl verify -CAfile certs/ca.cert.pem certs/server.cert.pem
# certs/server.cert.pem: OK
cat index.txt
# V  271108160204Z  1000  unknown  /C=CZ/ST=Prague/O=Homelab/CN=www.homelab.test

The V means valid; 1000 is the serial number from the serial file.

Step 3: Root → Intermediate → User chain

In real PKIs the root rarely signs end-user certificates. It signs an intermediate CA, and the root key goes offline. If the intermediate is compromised, you revoke it and the root survives.

Intermediate CA directory and config

mkdir -p /root/intermediate && cd /root/intermediate
mkdir certs crl newcerts private csr
chmod 700 private
touch index.txt
echo 1000 > serial
echo 1000 > crlnumber
cp /root/ca/openssl.cnf openssl.cnf
sed -i 's#^dir .*#dir = /root/intermediate#' openssl.cnf
sed -i 's#ca\.key\.pem#intermediate.key.pem#' openssl.cnf
sed -i 's#ca\.cert\.pem#intermediate.cert.pem#' openssl.cnf
sed -i 's#ca\.crl\.pem#intermediate.crl.pem#' openssl.cnf
sed -i 's#^policy .*#policy = policy_loose#' openssl.cnf

The intermediate uses policy_loose, so it can sign certificates for any organization.

Intermediate key, CSR and signature by the root

openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:4096 -aes-256-cbc -out private/intermediate.key.pem
chmod 400 private/intermediate.key.pem
openssl req -config openssl.cnf -new -sha256 -key private/intermediate.key.pem -out csr/intermediate.csr.pem -subj "/C=CZ/ST=Prague/O=Homelab/CN=Homelab Intermediate CA"

openssl ca -config /root/ca/openssl.cnf -extensions v3_intermediate_ca -days 3650 -notext -md sha256 -in csr/intermediate.csr.pem -out certs/intermediate.cert.pem
chmod 444 certs/intermediate.cert.pem
cat certs/intermediate.cert.pem /root/ca/certs/ca.cert.pem > certs/ca-chain.cert.pem

v3_intermediate_ca sets CA:true, pathlen:0: this CA may sign end-entity certificates but no further CAs.

User certificate signed by the intermediate

openssl req -new -newkey rsa:2048 -nodes -keyout private/user.key.pem -out csr/user.csr.pem -subj "/C=CZ/ST=Prague/O=Homelab/CN=Homelab User"
chmod 400 private/user.key.pem
openssl ca -config openssl.cnf -extensions usr_cert -days 375 -notext -md sha256 -in csr/user.csr.pem -out certs/user.cert.pem

The usr_cert profile gives TLS Web Client Authentication, E-mail Protection.

Verify the chain

openssl verify -CAfile /root/ca/certs/ca.cert.pem certs/intermediate.cert.pem
# certs/intermediate.cert.pem: OK
openssl verify -CAfile certs/ca-chain.cert.pem certs/user.cert.pem
# certs/user.cert.pem: OK

Verification walks upward: the user cert is checked against the intermediate, the intermediate against the root, and the root is trusted.

Step 4: Signing data and verifying it through the chain

A digital signature is a hash of the data, transformed with the signer's private key. Anyone with the matching public key can check it. The certificate chain answers the remaining question: whose public key is this?

cd /root/intermediate
echo "Signed by Homelab User" > data.txt
openssl dgst -sha256 -sign private/user.key.pem -out data.sig data.txt

The verifier first checks that the certificate itself is trustworthy, then takes the public key from it:

openssl verify -CAfile certs/ca-chain.cert.pem certs/user.cert.pem
# certs/user.cert.pem: OK
openssl x509 -in certs/user.cert.pem -pubkey -noout > user.pub.pem
openssl dgst -sha256 -verify user.pub.pem -signature data.sig data.txt
# Verified OK

Now tamper with the data and check again:

echo "tampered" >> data.txt
openssl dgst -sha256 -verify user.pub.pem -signature data.sig data.txt
# Verification failure
# ... rsa routines:ossl_rsa_verify:bad signature ...

One extra line breaks the signature. That gives integrity (the data did not change) and authenticity (it was signed by the holder of a certificate chaining to a trusted root).

Step 5: An ECC intermediate, revocation and a CRL

For the final step I wanted something closer to a real deployment: at least two intermediates, revocation in at least one of them, and a mix of RSA and ECC keys.

Second intermediate with an ECC P-384 key

mkdir -p /root/intermediate2 && cd /root/intermediate2
mkdir certs crl newcerts private csr && chmod 700 private
touch index.txt && echo 1000 > serial && echo 1000 > crlnumber
cp /root/ca/openssl.cnf openssl.cnf
# same five sed edits as in Step 3, with intermediate2 instead of intermediate

openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:P-384 -aes-256-cbc -out private/intermediate2.key.pem
chmod 400 private/intermediate2.key.pem
openssl req -config openssl.cnf -new -sha384 -key private/intermediate2.key.pem -out csr/intermediate2.csr.pem -subj "/C=CZ/ST=Prague/O=Homelab/CN=Homelab Intermediate CA 2 ECC"

openssl ca -config /root/ca/openssl.cnf -extensions v3_intermediate_ca -days 3650 -notext -md sha256 -in csr/intermediate2.csr.pem -out certs/intermediate2.cert.pem
cat certs/intermediate2.cert.pem /root/ca/certs/ca.cert.pem > certs/ca-chain.cert.pem
openssl verify -CAfile /root/ca/certs/ca.cert.pem certs/intermediate2.cert.pem

The RSA root can sign an ECC intermediate: the root's signature algorithm and the subject's key type are independent.

ECC user certificate

openssl req -new -newkey ec -pkeyopt ec_paramgen_curve:P-256 -nodes -keyout private/user2.key.pem -out csr/user2.csr.pem -subj "/C=CZ/ST=Prague/O=Homelab/CN=Homelab ECC User"
chmod 400 private/user2.key.pem
openssl ca -config openssl.cnf -extensions usr_cert -days 375 -notext -md sha256 -in csr/user2.csr.pem -out certs/user2.cert.pem
openssl verify -CAfile certs/ca-chain.cert.pem certs/user2.cert.pem
# certs/user2.cert.pem: OK

Revoking a certificate and publishing a CRL

To keep the Step 4 user certificate valid, I issued a throwaway certificate from the RSA intermediate and revoked that one:

cd /root/intermediate
openssl req -new -newkey rsa:2048 -nodes -keyout private/revokeme.key.pem -out csr/revokeme.csr.pem -subj "/C=CZ/ST=Prague/O=Homelab/CN=Revoked Test User"
openssl ca -config openssl.cnf -extensions usr_cert -days 375 -notext -md sha256 -in csr/revokeme.csr.pem -out certs/revokeme.cert.pem

openssl ca -config openssl.cnf -revoke certs/revokeme.cert.pem -crl_reason keyCompromise
openssl ca -config openssl.cnf -gencrl -out crl/intermediate.crl.pem
openssl crl -in crl/intermediate.crl.pem -noout -text

Revocation only marks the certificate as R in index.txt. Clients learn about it only from the CRL, which is why the second command matters. Now verify with CRL checking turned on:

openssl verify -crl_check -CAfile certs/ca-chain.cert.pem -CRLfile crl/intermediate.crl.pem certs/revokeme.cert.pem
# error 23 at 0 depth lookup: certificate revoked
cat index.txt

The certificate's signature and dates are still perfectly valid, yet it is rejected because the CA has withdrawn its trust.

Design choices

  • Root CA: RSA 4096, AES-256 encrypted, 20 years, key file 400. The longest-lived key with the widest compatibility; it should be kept offline.
  • Intermediate CA: RSA 4096, AES-256 encrypted, 10 years, key file 400. Does the daily signing and can be revoked without touching the root; pathlen:0.
  • Intermediate CA 2: ECC P-384, AES-256 encrypted, 10 years, key file 400. About 192-bit security with a far smaller key than RSA, and it adds algorithm diversity.
  • Server: RSA 2048, unencrypted, 375 days, key file 400. Short-lived and unencrypted so the service can start unattended.
  • Users: RSA 2048 or ECC P-256, unencrypted, 375 days, key file 400. 112 or 128-bit security is plenty for a one-year certificate.

Two rules sit behind these choices. A child certificate never outlives its issuer. And every private key is readable only by root, while certificates are public (444).

For this walkthrough I reused one pass phrase for all CA keys. In a real PKI, each CA key gets its own strong pass phrase, and the root key lives on offline storage or an HSM.

Mistakes I made (so you don't)

  • A missing /CN=. I typed -subj "/C=CZ/ST=Prague/O=Homelab Intermediate CA", which turned the whole name into the organization and left no Common Name. Under policy_strict the root would have refused it. Re-creating the CSR fixed it; the key did not need to change.
  • A missing leading slash. -subj "C=CZ/..." fails with subject name is expected to be in the format /type0=value0/....
  • Long one-line sed commands. A missing ; breaks the whole expression. Five short sed -i lines are far easier to get right by hand.
  • A stray privkey.pem. An interrupted openssl req -newkey without -keyout writes its key to privkey.pem by default. Delete it so no orphaned key is left behind.
  • "bad decrypt ... maybe wrong password". Just a mistyped pass phrase; the key file is fine.
